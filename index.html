GitHubとは（Gitとの違い）

Gitはパソコン上で履歴を記録する「バージョン管理ツール」です。

GitHubはその履歴やコードをインターネット上で共有・レビューする「ホスティング／コラボレーションサービス」です。

ローカルで作業し、GitHubに送ることでチームと同じコードベースで進められます。

  • Git：コミット・ブランチなど、履歴の操作は主に自分のマシンで行う。
  • GitHub：リモートのリポジトリ、Pull Request、Issue、レビュー、CI 連携など。
  • 別サービスに GitLab や Bitbucket もあるが、概念（clone / push / PR）はほぼ同じ。
初心者向け補足 「GitがなくてもGitHubのWebだけ」では、本格的な開発フローは組みにくいです。まずは Git の基本コマンドと GitHub の画面操作の両方を触ると理解が早いです。

基本用語集

日常開発で必ず出る5語＋αを、短く押さえます。

名前を覚えるより「いつ使うか」をイメージすると定着しやすいです。

以下はすべてこのページの他セクションでも繰り返し登場します。

  • Repository（リポジトリ）：プロジェクトのファイルと履歴の入れ物。ローカル／GitHub 上の両方に存在しうる。
  • Commit（コミット）：ある時点の変更を履歴として1単位で記録する操作・その記録そのもの。
  • Branch（ブランチ）：履歴の分岐。機能開発は新しいブランチで行い、後でまとめて取り込むのが一般的。
  • Pull Request（PR）：ブランチの変更を取り込んでもらうための依頼。レビュー・議論・マージの場。
  • Issue：バグ・要望・タスクをチケット化し、議論や紐付け（PR とリンク）に使う。
初心者向け補足 「コミット＝保存」ではなく「意味のあるまとまりで履歴に刻む」と考えると、あとで見返したときに助かります。

基本操作フロー（5ステップ）

チーム開発でよく使う流れは「ブランチを切る → 変更してコミット → リモートへ送る → PR → マージ」です。

この順番で読めば、画面とターミナルのどちらを開けばよいかが整理できます。

下図はその関係のラフ図です（詳細は「実演手順」で手を動かしながら確認）。

  1. ブランチを作成・切り替え：作業単位（機能・修正）ごとに分岐する。
  2. ファイルを編集：エディタで変更。ここではまだ履歴に載らない。
  3. ステージ → コミット：意図した変更だけをまとめて履歴に残す。
  4. push：ローカルのコミットを GitHub 上の同名ブランチへ送る。
  5. PR 作成 → レビュー → マージ：既定ブランチ（多くは main）へ取り込む。
初心者向け補足 手元だけで完結するのは「ブランチ〜コミット」まで。push 以降は GitHub 上の共有リポジトリと同期するイメージです。

実演手順（リポジトリ作成〜PRマージ）

GitHub で空のリポジトリを作り、ローカルから変更を送って PR でマージするまでの最短ルートです。

URL やブランチ名は自分の環境に読み替えてください。

まずは1回通しで実行し、あとから各コマンドの意味を見返すと理解が深まります。

  • GitHub で New repository を選び、リポジトリ名を決めて作成（README ありでもなしでも可）。
  • 表示される HTTPS URL をコピーし、ローカルでクローンする。
git clone https://github.com/あなたのユーザー名/リポジトリ名.git
cd リポジトリ名
  • 作業用ブランチを作成して切り替える。
git checkout -b feature/first-change
  • ファイルを編集したあと、変更をステージしてコミットする。
git add .
git commit -m "docs: 初回の変更を追加"
  • リモート（GitHub）へブランチごと送る。初回は -u で追跡ブランチを設定。
git push -u origin feature/first-change
  • PR 作成（GitHub 画面）：リポジトリページを開く → 黄色バナーの Compare & pull request、または Pull requests タブ → New pull request。
  • base（取り込み先、例: main）と compare（送る側ブランチ）を確認 → タイトル・説明を入力 → Create pull request。
  • レビュー後、Merge pull request → Confirm merge。ローカルでは main を最新化するときに git checkout main と git pull を使う。
初心者向け補足 git add . は「カレントディレクトリ以下の変更をすべてステージ」です。意図しないファイルが混ざることがあるので、慣れたら git status と git add <ファイル> で選ぶと安全です。

実演用 演習エリア

研修や説明時に、受講者と一緒に「今どの手順まで進んだか」を確認するための練習ブロックです。

左のチェックを進めると進捗表示が更新され、下のボタンで疑似ターミナルログを出せます。

実コマンド実行前のリハーサルとして使ってください。

進捗: 0 / 5 完了

[ready] 演習を開始できます。
使い方のコツ 受講者に「次の1コマンドは何か」を先に答えてもらってからボタンを押すと、受け身になりにくく理解が定着しやすいです。

ブランチ運用ルール

チームごとに細則は違いますが、「既定ブランチは常にデプロイ可能」「作業は短命ブランチ」がよくある型です。

ブランチ名で目的がわかると、PR と Issue のやり取りがスムーズになります。

ルールは README や社内ドキュメントに書かれていることが多いので、最初に一通り読む価値があります。

  • main（または master）：製品として安定した状態を置くブランチ。直接 push 禁止のチームも多い。
  • 作業ブランチ例：feature/ログイン画面、fix/計算ミス、chore/依存更新。
  • 長く放置したブランチはコンフリクトの元。小さめの変更で早めに PR に出す。
  • マージ後はローカルの作業ブランチを削除し、main を pull して次の作業へ。
初心者向け補足 「とりあえず main で全部やる」はコンフリクトやレビュー漏れの原因になりやすいです。最初からブランチを切る習慣をつけるとのちが楽です。

Pull Requestの書き方

PR は「変更のパッケージ」と「レビュアーへの説明書」です。書けば書くほどマージが速くなります。

何を・なぜ・どう確認すればよいかを短く明示するのがコツです。

Issue 番号を本文に含めると、マージ後に自動で紐付け・クローズできる場合があります（Fixes #123 など）。

  • タイトル：変更の要約。将来ログを追う人のため、曖昧な「修正」だけは避ける。
  • 背景・目的：1〜3行でよいので「課題」「期待する挙動」を書く。
  • 変更内容：箇条書きでファイル／挙動レベル。スクリーンショットや GIF は UI 変更に有効。
  • 確認手順：レビュアーが手元で再現できるチェック項目（例：ログイン → 設定画面を開く）。
  • リスク・未対応：既知の制限があれば先に書くと後戻りが減る。
初心者向け補足 ドラフト PR（Draft）を使えば、「まだ途中だが早めに見てほしい」と伝えつつ、誤マージを防げます。

Issueの使い方

Issue は「やること・直すこと」のチケット。会話の履歴と合意が残るのが強みです。

ラベル・マイルストーン・担当者で整理すると、優先度が見えやすくなります。

PR 本文やコミットメッセージから Issue を参照すると、トレーサビリティが上がります。

  • 起票：Issues → New issue。テンプレートがあるプロジェクトはそれに沿って記入。
  • 良い Issue の要素：現象／再現手順／期待値／環境（OS・ブラウザ・バージョン）。
  • 議論：コメントで補足。決定事項は冒頭か Wiki にまとめると後任に優しい。
  • PR とのリンク：PR 説明に Closes #番号 などを書くとマージ時に Issue を閉じられる（設定により異なる）。
初心者向け補足 「口頭だけで終わらせる」と同じ議題が何度も出がちです。小さくても Issue に残すクセがあるとチーム全体が楽になります。

よくあるミスと対処

誰でも一度は踏むポイントです。メッセージをそのまま検索すると公式ドキュメントや Stack Overflow に当たります。

迷ったら git status とリモートのブランチ状態を確認するのが近道です。

破壊的操作（履歴の書き換えなど）はチームルール確認のうえで。

  • push が拒否される：リモートに自分にないコミットがある。先に git pull（または git pull --rebase）で取り込み、再度 push。
  • 間違ったブランチでコミットした：まだ push していなら git reset や新ブランチ切り出しでリカバリ可能。push 済みならチームに相談。
  • コンフリクト：同じ行を別ブランチが編集。エディタで衝突マーカーを解消し、コミットして push。
  • .env など秘密を commit してしまった：すぐに管理者へ。履歴から消す必要がある場合は専用手順が必要。
  • 巨大ファイルを入れてしまった：リポジトリが重くなる。git lfs の検討や、履歴からの除去が必要になることがある。
初心者向け補足 「わからないまま force push」は他の人の履歴を壊すことがあります。共用ブランチでは禁止・要許可が多いです。

学習後チェックリストテスト環境です

自分で説明できるか・手が動くかを確認するための簡易リストです。

紙に印刷してチェックしても、ブラウザのブックマークと一緒に使っても構いません。

曖昧な項目があれば、このページの該当セクションに戻って復習してください。

  • Git と GitHub の違いを一言で言える。
  • Repository / Commit / Branch / PR / Issue を自分の言葉で説明できる。
  • ブランチを切り、コミットし、push し、PR を作成する一連が一人でできる。
  • PR に「目的・変更・確認手順」を書ける。
  • Issue に再現手順を書ける。
  • push が拒否されたとき、pull してから再度試す方針を知っている。
  • コンフリクトが「同時編集の衝突」だと理解している。
初心者向け補足 全部にチェックがつかなくても問題ありません。ハンズオンを繰り返すほど、説明できる項目が増えていきます。
